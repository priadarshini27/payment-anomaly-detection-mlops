## The PaySim dataset

PaySim is a synthetic mobile-money transaction dataset generated by an
agent-based simulator, calibrated against one month of real transaction
logs from an African mobile financial service provider. Because real
financial transaction logs are almost never released publicly, PaySim is
a standard benchmark in fraud-detection research: it reproduces the
statistical shape of real mobile-money traffic — including its extreme
class imbalance — without exposing real customer data.

It simulates five transaction types across a 30-day period (744 hourly
steps):

- **CASH_IN** — a customer deposits cash into their mobile-money account.
- **CASH_OUT** — a customer withdraws cash from their account.
- **DEBIT** — funds move from a mobile-money account to a bank account.
- **PAYMENT** — a customer pays a merchant for goods or services.
- **TRANSFER** — funds move from one customer account to another.

Download: https://www.kaggle.com/datasets/ealaxi/paysim1

### Column reference

| Field | Type | Description |
|---|---|---|
| `step` | int | Simulation time unit; 1 step = 1 hour (1–744 total). |
| `type` | categorical | CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER. |
| `amount` | float | Transaction value in local currency. |
| `nameOrig` | string | Originating customer identifier (prefix `C`). |
| `oldbalanceOrg` | float | Originator's balance before the transaction. |
| `newbalanceOrig` | float | Originator's balance after the transaction. |
| `nameDest` | string | Recipient identifier (`C` = customer, `M` = merchant). |
| `oldbalanceDest` | float | Recipient's balance before (0 for merchants). |
| `newbalanceDest` | float | Recipient's balance after the transaction. |
| `isFraud` | binary | Ground-truth label. **Used only for evaluation, never as a feature.** |
| `isFlaggedFraud` | binary | Rule-based flag from PaySim's own business-rule simulator. Not a second label. |

### Why class imbalance is the central design constraint

Fraudulent transactions are roughly **0.13%** of all records (8,213 of
6,362,620 in the full release), confined almost entirely to `TRANSFER`
and `CASH_OUT`. This rules out accuracy as an evaluation metric (a model
predicting "not fraud" for everything scores >99.8%) and motivates the
project's unsupervised approach: with so few positive examples, a
supervised classifier tends to memorize the specific fraud patterns
present in the simulation rather than generalize to novel anomaly types.

## The EDA workflow

Before any cleaning or modeling code was written, the full dataset was
explored in `eda/eda.ipynb`, following a fixed sequence of increasingly
specific questions (per the project's EDA methodology): inspect the
dataset → understand variables → find missing values → detect duplicates
→ analyze distributions → study relationships → detect outliers → assess
data quality → identify cleaning requirements → generate a clean dataset.

Every cleaning decision made in `preprocessing/clean_data.py` (see
[03-data-cleaning.md](03-data-cleaning.md)) traces back to a specific,
confirmed finding from this notebook, not a generic checklist run out of
habit.

## Confirmed findings (from the full 6,362,620-row dataset)

These are measured results, not assumptions — reproducible by re-running
`eda/eda.ipynb` top to bottom (Restart & Run All).

| Check | Result |
|---|---|
| Missing values | **0** across all 11 columns |
| Fully duplicated rows | **0** |
| Negative amounts / balances | **0** across all 5 money columns |
| Zero-amount transactions | **16**, and **every one is labeled fraud** |
| Self-transactions (`nameOrig == nameDest`) | **0** |
| `isMerchantDest` count vs. `PAYMENT` count | **Exactly equal** — confirms the `C`/`M` prefix convention: every `PAYMENT` goes to a merchant, and only `PAYMENT` transactions do |
| Overall fraud rate | **0.129%** (8,213 / 6,362,620) |
| Fraud rate by type | `TRANSFER` 0.769%, `CASH_OUT` 0.183%, `CASH_IN`/`PAYMENT`/`DEBIT` **0%** |
| Origin-account full-drain rate, fraud vs. legitimate | **97.7%** of fraud transactions leave `newbalanceOrig == 0`, vs. **23.8%** of legitimate ones |
| `isFlaggedFraud` rule performance | Fires only **16** times total; 100% precision but negligible recall (misses 8,197 of 8,213 fraud cases) |
| `amount` distribution | Heavily right-skewed; mean far above median, motivating the `log1p` transform |
| Balance residuals (`oldbalance − amount − newbalance ≠ 0`) | A structural property of PaySim's fraud-injection logic, not data corruption — kept and engineered into a feature rather than cleaned away |
| Time-of-day / day-of-week fraud pattern | No single hour or day stands out strongly — weak time signal, expected in a simulated dataset |

### Why each finding matters downstream

- **Zero missing values** → no imputation strategy needed anywhere in
  `preprocessing/clean_data.py::handle_missing`; the function still runs
  the check on every load as a safety net for a future data source, but
  it is expected to be a no-op on PaySim itself.
- **Zero duplicates** → `drop_duplicates()` is likewise a no-op on this
  dataset, but the rule is real: an ingestion retry would otherwise
  silently inflate `txnVelocity1h`/`txnVelocity24h`.
- **16 zero-amount, all-fraud rows** → these are dropped as invalid
  financial records (`validate_amounts`), a deliberate and documented
  trade-off since it removes 16 true fraud rows out of 8,213. See
  [03-data-cleaning.md](03-data-cleaning.md) for the full reasoning.
- **Non-zero balance residuals as a structural artifact** → directly
  produces the `balanceDeltaOrig` / `balanceDeltaDest` engineered
  features (never used as a row-filtering rule).
- **97.7% vs 23.8% drain rate** → directly produces the `origZeroedOut`
  binary feature, one of the most discriminative signals in the dataset.
- **Fraud confined to TRANSFER/CASH_OUT** → directly justifies one-hot
  encoding `type` and segmenting fraud-rate analysis by type throughout
  the dashboard and evaluation code.
- **Right-skewed `amount`** → directly produces the `logAmount` feature.

## Reproducing the notebook

```bash
jupyter lab eda/eda.ipynb
# Kernel → Restart & Run All
```

The notebook expects `data/paysim.csv` to already be in place (see
[01-getting-started.md](01-getting-started.md), Step 3). It is
exploratory by design — read-only against the raw CSV, and does not write
to `data/paysim_clean.csv` or the database. The deterministic,
production-grade equivalent of its cleaning logic lives in
`preprocessing/clean_data.py`, documented next.
